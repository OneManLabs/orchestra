# Orchestra V2 operations

## Production topology

Run one Core on an always-on host, install one native Agent per managed device, and keep the Desktop/Web client on operator devices. Put all three behind Tailscale grants or a private network. Core is the only control-plane listener; Agents make outbound credential-authenticated WebSocket connections.

For the first production release, Core uses a durable, atomically replaced state document and one active Core process. The Kubernetes manifest deliberately uses one replica and `ReadWriteOnce`; increasing replicas without a shared transactional database is unsafe. A PostgreSQL/Redis HA backend is an enterprise scale adapter, not something this repository pretends to provide today.

## Required secrets

- `FLEET_TOKEN`: recovery/admin bearer token, at least 32 random bytes for non-loopback deployment. A loopback Core without this variable generates an owner-only recovery-token file and still requires authentication.
- `FLEET_MASTER_KEY`: base64-encoded 32-byte AES key used by the built-in encrypted secret store.
- Device credentials: generated by one-time enrollment and stored by each Agent with owner-only permissions.
- Signing credentials: supplied only in an isolated release pipeline; never put Apple, Microsoft, RPM, or repository signing keys in this repository.

Generate local secrets:

```bash
openssl rand -hex 32
openssl rand -base64 32
```

The `--allow-unauthenticated-loopback` switch is only for isolated development/test processes. Do not use it for any Core reached through a reverse proxy, container port publication, SSH forwarding, or another user's local session; those paths can make an untrusted caller appear to originate from loopback.

Issue ordinary API tokens with a base `read` or `write` scope and add only the sensitive families they need. For example, an automation service that maintains policies needs `write` plus `policies:write`; a generic `write` token cannot alter policy controls. Keep the recovery token out of routine clients so it remains a usable break-glass credential.

## Enrollment

1. An administrator creates an enrollment token in Desktop or `POST /api/v2/enrollment/tokens`.
2. The plaintext token is returned once. Core stores only a hash, expiry, use count, and requested role/group metadata.
3. Start the Agent with `FLEET_ENROLLMENT_TOKEN`. It exchanges the token at `/api/v2/enrollment/exchange` for a device-bound credential.
4. The Agent writes that credential to its private data directory with mode `0600` where supported.
5. Rename, assign a role/site/group, and verify capability/trust information in Orchestra.
6. Decommissioning revokes the credential before removing runtime access.

QR enrollment encodes the Core URL and short-lived token. Treat an unexpired QR code as a credential.

Native Agent installation, secure unattended preseeding, package build commands, and purge semantics are documented in [`packages/agent/install/README.md`](../packages/agent/install/README.md). Windows and Linux automation accepts root/administrator-only configuration or token files so one-time enrollment credentials do not need to appear in process arguments or package-manager logs.

## Updates

Agent release records include platform, architecture, protocol range, SHA-256 checksum, download URL, and optional signature. Rollouts target devices/groups, validate protocol/platform compatibility, honor a scheduled start, gate maintenance-only targets, and pause after the configured canary cohort so an operator can inspect results before resuming the remaining devices. They can request apply or rollback through the Agent, subject to the privileged-installer handoff below.

Agent-side apply is a verified staging operation, not privilege escalation. It returns `pending-service-installer` and waits for a separately administered root/SYSTEM deployment service to inspect and install the native package. The required trust checks, package-manager commands, health confirmation, failure record, and rollback boundary are specified in [the installer handoff documentation](../packages/agent/install/README.md#staged-update-service-handoff). No checked-in service automatically consumes `active.json`, so a rollout must not be called successful until the reconnected Agent reports the expected installed version.

The repository contains package/service definitions, but release signing requires external identities:

| Platform | External prerequisite |
| --- | --- |
| macOS `.pkg` | Apple Developer ID Installer certificate, hardened runtime/notarization credentials |
| Windows `.msi` | Authenticode certificate and trusted timestamp service |
| Debian/Ubuntu | APT repository and GPG signing key |
| RPM distributions | RPM repository and GPG signing key |
| Offline bundle | Offline root key plus an exported, signed release manifest |

Unsigned development packages remain visibly marked and should not be promoted to beta or stable channels. The checked-in GitHub workflow deliberately refuses those channels. It assembles complete development PKG/MSI/DEB/RPM candidates, but it does not possess or invoke platform signing, notarization, or repository identities.

## Container and service deployment

- Docker Compose reads `deploy/.env`, mounts recovery/vault values as secret files, uses a read-only root filesystem, and persists Core/Agent state in named volumes.
- The systemd and launchd templates are documented in `deploy/core-services/README.md`. The macOS wrapper—not Core itself—loads the protected environment file.
- The user-session macOS wrapper in `deploy/launchd/run-core-macos-user.sh` reads `recovery-token` and `master-key` from the `com.fleetcanvas.core` Keychain service by default. For unattended migration, set `FLEET_TOKEN_FILE` and `FLEET_MASTER_KEY_FILE` to regular, non-symlink files owned by the launch user with mode `0600` or stricter; never embed either secret directly in a launchd plist.
- Before applying Kubernetes, create `fleet-core-secrets` with `FLEET_TOKEN` and `FLEET_MASTER_KEY`, and `fleet-core-config` with a reachable `public-url`. The manifest intentionally has one replica.

Example Kubernetes prerequisites using files to keep secret values out of command arguments:

```bash
kubectl create secret generic fleet-core-secrets \
  --from-file=FLEET_TOKEN=./fleet-token \
  --from-file=FLEET_MASTER_KEY=./fleet-master-key
kubectl create configmap fleet-core-config \
  --from-literal=public-url='https://fleet-core.example.ts.net'
kubectl apply -f deploy/kubernetes/core.yaml
```

## Backups and disaster recovery

Core backup captures control-plane state, version metadata, and integrity checksum. Artifact bytes remain in their configured NAS/S3 provider and need that provider's own snapshot/replication policy.

Recommended schedule:

- Hourly Core backup retained for 48 hours.
- Daily backup retained for 30 days.
- Weekly encrypted off-site backup retained per organizational policy.
- NAS snapshots for artifacts/datasets, replicated to a physically separate destination.
- Quarterly restore exercise.

Recovery procedure:

1. Stop Core and copy the damaged data directory for forensics.
2. Provision the same or a newer compatible Core version.
3. With Core running in an isolated recovery window, stage the restore through the backup API with `{ "confirm": true }`. A `.fleet-backup` file is encrypted and is not a drop-in replacement for `fleet-state.json`.
4. Confirm the API returned `restoreStaged: true` and `restartRequired: true`, then restart Core. Startup atomically promotes the validated state image before accepting connections.
5. Run diagnostics and verify audit-chain integrity.
6. Rotate the recovery token and master key if compromise is suspected.
7. Revoke unknown device/API credentials and require affected Agents to enroll again.
8. Verify NAS storage connections and run artifact checksum verification.

The restore endpoint never replaces live runtime objects. It validates integrity, decryption, document shape, version compatibility, and the audit chain; creates a pre-restore safety backup; and writes a pending image that is applied only on the next Core restart. It also requires an explicit confirmation value.

## Air-gapped operation

- Bind Core to an isolated management network.
- Block Core webhook/HTTP destinations with policy and `FLEET_HTTP_ALLOWED_HOSTS`, and use host/container egress controls for Agent shell and Codex processes.
- Transfer signed native Agent packages through the organization's approved offline software-distribution process. Orchestra records and verifies release checksums/signatures, but this repository does not ship an offline-bundle importer or package-signing identity.
- Use local Codex/model tooling only when external API calls are prohibited.
- Export audit/compliance evidence through an approved removable-media procedure.
- Configure Orchestra policy/classification/zone rules, Core HTTP host allowlists, and separate host/container command and egress controls.

An air-gapped deployment needs locally operated certificate issuance/trust, notification delivery, identity, package distribution, and model services where those functions are required.

## Maintenance

- Review open alerts, update drift, failed jobs, and backup verification daily.
- Review device trust, API tokens, enrollment tokens, and policy exceptions weekly.
- Rotate secrets and test restores on schedule.
- Put devices in maintenance mode before hardware work; the scheduler will not send them new work.
- Use diagnostics/support bundles with redaction enabled before sharing them.

## Safe power control

Wake-on-LAN requires a target MAC address and an online relay Agent; the broadcast address is optional. The scheduler can select an eligible offline device, request one bounded wake operation, and dispatch the queued job after reconnection. Configured post-job idle sleep/shutdown waits until terminals, sessions, jobs, transfers, desktop sessions, pipeline work, and update activity are clear, and it is suppressed by maintenance mode and quiet hours. Sleep, restart, shutdown, lock, and logout require the target Agent's explicit power-action opt-in. Pipelines should use approval gates for destructive power actions. UPS integration and smart-plug control are not included; an external UPS controller should prefer graceful shutdown and must not depend solely on Core being reachable.
